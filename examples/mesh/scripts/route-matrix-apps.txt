# 行格式（三种，字段数不同，由 trace-audit.py 解析；改这里 MUST 同步改 bring-up.sh 的 PROBE_ROUTES）：
#   普通行    ：路径|方法|目标域|期望 service span 前缀|请求体(可选)      —— 4~5 段
#   `+cache`  ：+cache|目标域|路径|方法|期望 span|回源排除 span        —— 6 段
#   `+async`  ：+async|目标域|期望 span                               —— 3 段
#   * 路径写**外部**形态（带 /api）；根 span 名是 rewrite 之后的形态（不带 /api），
#     两边都能对上（trace-audit.py 的 root_op_candidates 同时认两种写法）。
#   * 目标域/span 写 `-` = 该路由刻意不触达任何域（/ping 是存活性自响应），
#     不设业务 span 期望，但「窗口内有这条 trace」与「有 sidecar span」照判。
#   * `+async` 行：不以 HTTP 路由形态出现（points 域的写路径不经 HTTP），
#     判据是「同一条 trace 内既有下单 span 又有消费 span」——即 mqx 的注入/提取生效。
#   * `+cache` 行：同一路由连读两次，判「前一次回源（含回源 span）+ 后一次命中
#     （不含回源 span）」。它判的是**缓存行为**，不是入口链路，故单独成行 ——
#     与上面的 `/api/product/1` 普通行不重复：那行只证明「入口→域业务层通」。
# 改这里 MUST 同步改 bring-up.sh 的 PROBE_ROUTES（两处必须逐条一致）。
